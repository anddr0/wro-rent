# Решения по проекту

Журнал принятых решений: что решили и почему. Новые решения дописываем в нужный
раздел с датой. Если решение меняется — не удаляем старое, а помечаем
«заменено» и пишем новое рядом, чтобы была видна история.

## Архитектура

**Одно Next.js-приложение в корне репозитория** (2026-10-31)
Всё в `src/`: `app` (роутинг), `bot` (логика бота), `server` (серверный код), `lib` (браузерный и общий).
Почему: после перехода бота на вебхук приложение одно — монорепозиторий только добавлял
лишние `package.json`, симлинки и команды с `-w`. Обычная Next-структура понятнее.
Если появится второе самостоятельное приложение (отдельная админка, воркер) — вернёмся к монорепозиторию.

~~**Монорепозиторий на npm workspaces**~~ (2026-10-31) — _заменено решением выше._
`apps/web` — Next.js-приложение, `packages/bot` — логика бота, `packages/db` — типы базы.
Было оправдано, пока бот работал отдельным процессом (polling).

**Бот работает через вебхук внутри Next.js** (2026-10-31)
Telegram шлёт обновления на `/api/telegram/webhook`, polling не используем нигде.
Почему: один деплой вместо двух, не нужен постоянно работающий сервер; дев и прод работают одинаково.
Следствие: фоновые задачи (напоминания и т.п.) — через расписание (Vercel Cron или pg_cron), не через вечный процесс.

**Структура `src`: `app` / `bot` / `server` / `lib`** (2026-10-31)
`app` — только роутинг, `server` — только серверный код, `lib` — браузерный и общий.
Почему: стандартный для Next вариант «код вне `app`», а отдельная `server` сразу показывает, где живут секреты.

**Prettier с настройками по умолчанию** (2026-11-01)
Код форматирует Prettier, ESLint отвечает только за ошибки (`eslint-config-prettier` отключает его стилевые правила).
Почему: стиль не тема для ревью; настройки по умолчанию — меньше споров и конфигов.
Сгенерированные файлы (`database.types.ts`, `AGENTS.md`) в `.prettierignore`, чтобы не шуметь в диффах.

**Node.js 22** (2026-10-31)
Почему: актуальный supabase-js не работает на Node 20 (нет встроенного WebSocket).

## Окружения

**Два бота: dev и prod** (2026-10-31)
`@vitya_bike_rent_bot` — dev, его вебхук смотрит на постоянный ngrok-домен. Для прода создаём отдельного бота.
Почему: у одного бота может быть только один вебхук, иначе дев и прод перебивали бы друг друга.

**Dev — локальный Supabase в Docker, облачный проект — прод** (2026-10-31)
Почему: тестовые данные не попадают в прод, схему можно ломать и пересоздавать без последствий.

**Входа без Telegram в деве нет** (2026-10-31)
Мини-апп в деве открываем только через Telegram (ngrok).
Почему: не хотим обход авторизации в коде; поднять туннель несложно.

## База данных

**Схема меняется только миграциями** (2026-10-31)
Миграции только вперёд: отката нет, отмена — новой миграцией. Применённые миграции не редактируем.
Почему: история схемы в git, любую базу можно воспроизвести с нуля.

**Модель данных** (2026-10-31)

- Одна точка проката — таблицы точек нет.
- Клиент бронирует конкретный велосипед. Каждый велосипед — отдельная позиция:
  моделей и количества нет, даже если велосипеды одинаковые (2026-11-06).
- Доступность велосипеда — флаг `bikes.is_available`; занятость считается по броням, не хранится.
- Цены — только общие тарифы `rental_plans`, одинаковые для всех велосипедов (2026-11-06).
- ~~Персональная цена велосипеда по тарифу (`bike_price_overrides`, итог в `bike_plan_prices`)~~ —
  _заменено решением выше_: заказчик решил, что персональные цены не нужны.
- Бронь без тарифа (`plan_id = null`) — индивидуальная договорённость, например почасовая.
- Цена фиксируется в брони в момент бронирования.
- Клиент выбирает дату и время начала, окончание — начало плюс длительность тарифа.
  Даты брони админ не меняет, только цену (2026-11-07).
- Аватар пользователя — ссылка из Telegram (`users.photo_url`), обновляется при каждом входе;
  в своё хранилище не копируем (2026-11-01).
- Пересечение активных броней одного велосипеда запрещено на уровне базы (exclusion constraint).
- Оплата на месте или переводом BLIK, валюта PLN. Онлайн-оплаты нет.
- Заявка в ожидании даты не занимает. Когда админ подтверждает одну заявку, остальные
  заявки в ожидании на пересекающиеся даты отклоняются автоматически (2026-11-07).

Отказались: категории велосипедов, размер рамы, статусы велосипеда (ремонт/списан) —
пока не нужны, добавим миграцией при необходимости.

## Продукт

**Уведомления о новых заявках получают все админы** (2026-11-07)
Почему: админов мало, настройка «получать / не получать» — лишняя работа для MVP.

**Брони вручную в MVP нет** (2026-11-07)
Админ не создаёт брони сам — только через заявки клиентов. Вернёмся после запуска.

## Доступ и безопасность

**Браузер в Supabase не ходит** (2026-10-31)
Все запросы идут через наш сервер с секретным ключом. RLS включён на всех таблицах без политик — это страховка.
Почему: права проще писать и проверять в TypeScript; при входе через Telegram у Supabase нет своей сессии пользователя.
Если понадобится realtime — вернёмся к этому (свой JWT + политики RLS).

**Новые ключи Supabase (`sb_secret_…`)** (2026-10-31)
Почему: секретный ключ можно отозвать по отдельности, не ломая остальное, и он не работает из браузера.

**Авторизация через Telegram initData** (2026-10-31)
Мини-апп шлёт `Authorization: tma <initData>`, сервер проверяет подпись токеном бота.
Роли — в `users.role` (`customer` / `admin`). Первого админа назначаем вручную SQL-запросом.
Почему заголовок, а не cookie: в Telegram Desktop/Web мини-апп открыт в iframe, где cookie часто блокируются.

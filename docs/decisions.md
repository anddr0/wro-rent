# Решения по проекту

Журнал принятых решений: что решили и почему. Новые решения дописываем в нужный
раздел с датой. Если решение меняется — не удаляем старое, а помечаем
«заменено» и пишем новое рядом, чтобы была видна история.

## Архитектура

**Одно Next.js-приложение в корне репозитория** (2026-10-31)
Всё в `src/`: `app` (роутинг), `bot` (логика бота), `server` (серверный код), `lib` (браузерный и общий).
Почему: после перехода бота на вебхук приложение одно — монорепозиторий только добавлял
лишние `package.json`, симлинки и команды с `-w`. Обычная Next-структура понятнее.
Если появится второе самостоятельное приложение (отдельная админка, воркер) — вернёмся к монорепозиторию.

~~**Монорепозиторий на npm workspaces**~~ (2026-10-31) — _заменено решением выше._
`apps/web` — Next.js-приложение, `packages/bot` — логика бота, `packages/db` — типы базы.
Было оправдано, пока бот работал отдельным процессом (polling).

**Бот работает через вебхук внутри Next.js** (2026-10-31)
Telegram шлёт обновления на `/api/telegram/webhook`, polling не используем нигде.
Почему: один деплой вместо двух, не нужен постоянно работающий сервер; дев и прод работают одинаково.
Следствие: фоновые задачи (напоминания и т.п.) — через расписание (Vercel Cron или pg_cron), не через вечный процесс.

**Структура `src`: `app` / `bot` / `server` / `lib`** (2026-10-31)
`app` — только роутинг, `server` — только серверный код, `lib` — браузерный и общий.
Почему: стандартный для Next вариант «код вне `app`», а отдельная `server` сразу показывает, где живут секреты.

**Экраны рисуются в браузере, после загрузки пользователя** (2026-11-12)
`CurrentUserProvider` показывает страницы только после `/api/me`: initData от Telegram есть
только в браузере, сервер заранее не знает, кто открыл мини-апп.
Поэтому dev-проверку Next «мгновенная ли навигация» включаем только там, где её явно просят
(`instantInsights.validationLevel: "manual-warning"` в `next.config.ts`): по умолчанию она
рендерит каждую страницу на сервере и на каждой сообщала, что страница «выпала».

**Prettier с настройками по умолчанию** (2026-11-01)
Код форматирует Prettier, ESLint отвечает только за ошибки (`eslint-config-prettier` отключает его стилевые правила).
Почему: стиль не тема для ревью; настройки по умолчанию — меньше споров и конфигов.
Сгенерированные файлы (`database.types.ts`, `AGENTS.md`) в `.prettierignore`, чтобы не шуметь в диффах.

**Node.js 22** (2026-10-31)
Почему: актуальный supabase-js не работает на Node 20 (нет встроенного WebSocket).

## Окружения

**Два бота: dev и prod** (2026-10-31)
`@vitya_bike_rent_bot` — dev, его вебхук смотрит на постоянный ngrok-домен. Для прода создаём отдельного бота.
Почему: у одного бота может быть только один вебхук, иначе дев и прод перебивали бы друг друга.

**Dev — локальный Supabase в Docker, облачный проект — прод** (2026-10-31)
Почему: тестовые данные не попадают в прод, схему можно ломать и пересоздавать без последствий.

**Прод: Vercel + облачный Supabase, оба в Париже** (2026-11-07)
Supabase — `eu-west-3`, функции Vercel — `cdg1` (`vercel.json`).
Почему: каждый API-запрос ходит в базу, иногда не один раз. Из США в Европу это
~100 мс на каждый поход, а внутри одного города — единицы миллисекунд.

**Входа без Telegram в деве нет** (2026-10-31)
Мини-апп в деве открываем только через Telegram (ngrok).
Почему: не хотим обход авторизации в коде; поднять туннель несложно.

## База данных

**Схема меняется только миграциями** (2026-10-31)
Миграции только вперёд: отката нет, отмена — новой миграцией. Применённые миграции не редактируем.
Почему: история схемы в git, любую базу можно воспроизвести с нуля.

**Модель данных** (2026-10-31)

- Одна точка проката — таблицы точек нет.
- Клиент бронирует конкретный велосипед. Каждый велосипед — отдельная позиция:
  моделей и количества нет, даже если велосипеды одинаковые (2026-11-06).
- Доступность велосипеда — флаг `bikes.is_available`; занятость считается по броням, не хранится.
- Цены — только общие тарифы `rental_plans`, одинаковые для всех велосипедов (2026-11-06).
- ~~Персональная цена велосипеда по тарифу (`bike_price_overrides`, итог в `bike_plan_prices`)~~ —
  _заменено решением выше_: заказчик решил, что персональные цены не нужны.
- Бронь без тарифа (`plan_id = null`) — индивидуальная договорённость, например почасовая.
- Цена фиксируется в брони в момент бронирования.
- Клиент выбирает дату и время начала, окончание — начало плюс длительность тарифа.
  Даты брони админ не меняет, только цену (2026-11-07).
- Аватар пользователя — ссылка из Telegram (`users.photo_url`), обновляется при каждом входе;
  в своё хранилище не копируем (2026-11-01).
- Пересечение активных броней одного велосипеда запрещено на уровне базы (exclusion constraint).
- Оплата на месте или переводом BLIK, валюта PLN. Онлайн-оплаты нет.
- Заявка в ожидании даты не занимает. Когда админ подтверждает одну заявку, остальные
  заявки в ожидании на пересекающиеся даты отклоняются автоматически (2026-11-07).

**Фото велосипедов — публичный бакет Storage, отдаём со своего домена** (2026-11-14)
Файлы — в бакете `bike-photos`, порядок и привязка к велосипеду — в таблице `bike_photos`,
первое фото — обложка. Бакет публичный: фото и так видит любой клиент. Мини-апп берёт фото
по адресу `/bike-photos/...`, а Next пересылает запрос в Storage (rewrite в `next.config.ts`).
Почему: подписанные ссылки сложнее и хуже кэшируются; со своего домена браузер не ходит
в Supabase, а в деве фото открываются и с телефона. Оптимизацию картинок Next/Vercel
не используем — на бесплатном тарифе у неё лимит; размер уменьшим при загрузке (срез 5.3).

Отказались: категории велосипедов, размер рамы, статусы велосипеда (ремонт/списан) —
пока не нужны, добавим миграцией при необходимости.

## Продукт

**Название — WroRent** (2026-11-09)
В интерфейсе и у прод-бота (`@wro_rent_bot`). Имя папки и пакета `vityas_bike_rent` пока не трогаем.

**Навигация без вкладок, главная зависит от роли** (2026-11-11)
Главная — хаб, остальные экраны открываются кнопками, назад — стрелка Telegram.
Клиент на главной видит каталог и свои брони, админ — сводку на сегодня и разделы админки;
каталог глазами клиента админу доступен по ссылке. Экраны — в [`wireframes/`](wireframes/README.md).
Почему: экранов у клиента мало, вкладки только отнимали бы место; админу главная нужна для работы, а не для покупки.
Роль мини-апп берёт из `/api/me`; скрытие экранов — удобство, защита — `requireAdmin` в API.

**Дизайн — тема из tweakcn, светлая или тёмная по Telegram** (2026-11-11)
Цвета, скругления и тени — из [темы tweakcn](https://tweakcn.com/themes/cmho4nr9l000h04l1gu419ckw):
монохромная, скругление 1rem. Токены перенесены руками в `globals.css`, имена — как в shadcn/ui.
Светлая или тёмная палитра — по теме Telegram у пользователя, шапка Telegram красится в цвет фона.
Шрифт — Manrope: DM Sans из темы не поддерживает кириллицу.
Почему: чистый спокойный вид, а свои цвета не зависят от того, какую тему Telegram выбрал пользователь.
shadcn CLI не ставим: из темы нужны только токены. Если понадобятся готовые компоненты
(например, календарь в срезе 2.2) — подключим, имена токенов уже совпадают.

**Иконки — lucide-react; главное действие экрана — кнопка внизу** (2026-11-12)
lucide — тот же набор, что в shadcn/ui: простые линейные иконки, импорт по одной.
Главная кнопка экрана («Добавить велосипед», «Подтвердить») закреплена внизу (`BottomBar`), всегда под пальцем.
Нативную MainButton Telegram пока не используем: её цвет и вид хуже сочетаются с темой,
и две кнопки рядом («Отклонить» · «Подтвердить») в ней не сделать.

~~**Цвета: нейтральные — от Telegram, акцент — свой**~~ (2026-11-11) — _заменено решением выше._
Фон и текст берём из темы Telegram (светлая и тёмная работают сами), основные кнопки и акценты — свои.
UI-кит `@telegram-apps/telegram-ui` не ставим — только смотрим на него как на образец.
Почему: кит заявляет поддержку только React 18 и давно не обновлялся.

**Уведомления о новых заявках получают все админы** (2026-11-07)
Почему: админов мало, настройка «получать / не получать» — лишняя работа для MVP.

**Телефон клиента не собираем** (2026-11-11)
Связь — через бота и кнопку «Написать админу». Перед заявкой проверяем, что бот может писать клиенту.
Почему: минимизация персональных данных (GDPR) — не храним то, без чего можно обойтись.
Колонка `users.phone` пока остаётся пустой; уберём миграцией, если так и не понадобится.

**Брони вручную в MVP нет** (2026-11-07)
Админ не создаёт брони сам — только через заявки клиентов. Вернёмся после запуска.

**Переводы — свой словарь, а не библиотека** (2026-11-13)
Словари — обычные объекты по языкам (`src/lib/i18n/messages`), `t()` подставляет `{параметры}`
и выбирает форму множественного числа через встроенный `Intl.PluralRules`. `ru.ts` — эталон,
TypeScript требует в остальных языках те же ключи. Бот берёт тот же словарь.
Почему: язык хранится у пользователя, а не в адресе, страницы рисуются в браузере —
возможности библиотек вроде next-intl (язык в URL, серверный рендер, ICU) нам не нужны,
а свой код — полсотни строк без магии.

**Язык: выбор в настройках, иначе Telegram, иначе польский** (2026-11-13)
`users.locale` — выбранный вручную язык (null, пока не выбирал), вход его не перезаписывает.
`users.language_code` — язык Telegram, обновляется при каждом входе: по нему пишем тем,
кто язык не выбирал, в том числе в боте. Сейчас есть польский и русский; английский и
украинский база уже принимает, словари добавим перед запуском (блок 7).

**Данные на экранах грузим через SWR** (2026-11-13)
`useApi(path)` (`src/lib/use-api.ts`) — обёртка над `useSWR` и `apiFetch`.
Почему: ответы кэшируются по адресу — возврат на экран показывает данные сразу и тихо их обновляет,
одинаковые запросы с разных экранов (главная и каталог) идут один раз, данные обновляются,
когда пользователь возвращается в мини-апп. Свой хук пришлось бы дописывать до того же самого.
404 и другие ошибки клиента не повторяем, ошибки сервера — до трёх раз.

## Доступ и безопасность

**Браузер в Supabase не ходит** (2026-10-31)
Все запросы идут через наш сервер с секретным ключом. RLS включён на всех таблицах без политик — это страховка.
Почему: права проще писать и проверять в TypeScript; при входе через Telegram у Supabase нет своей сессии пользователя.
Если понадобится realtime — вернёмся к этому (свой JWT + политики RLS).

**Новые ключи Supabase (`sb_secret_…`)** (2026-10-31)
Почему: секретный ключ можно отозвать по отдельности, не ломая остальное, и он не работает из браузера.

**Авторизация через Telegram initData** (2026-10-31)
Мини-апп шлёт `Authorization: tma <initData>`, сервер проверяет подпись токеном бота.
Роли — в `users.role` (`customer` / `admin`). Первого админа назначаем вручную SQL-запросом.
Почему заголовок, а не cookie: в Telegram Desktop/Web мини-апп открыт в iframe, где cookie часто блокируются.
